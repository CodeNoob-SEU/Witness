# 设计取舍

这份文档记录 Witness 的关键决策**以及它们的代价**。每条都按同一个格式写：决策是什么、
为什么这么选、放弃了什么、什么情况下这个选择是错的。

代码里能读到「怎么做」，读不到「为什么不那样做」——这里补的是后者。

## 一条主线

> **已提交的事件是唯一事实；其它一切都是可以删掉重建的投影。**

三条不变量由此推出：

1. **先记录意图，再执行副作用。** 模型调用和工具执行都有明确的 durable 提交边界。
2. **日志是事实，Snapshot 是缓存。** 删除任何投影后仍可从 sequence 1 精确重建。
3. **可观测性不参与正确性。** 采样、导出失败、Collector 挂掉都不影响任务执行与恢复。

后面每一条决策，本质上都是在守这三条中的某一条。

---

## 1. 追加式事件日志，而不是可变状态表

**决策**：Run 的状态不存在任何一张表里，它是事件流折叠出来的。

**为什么**：Agent 任务最难的不是跑通，是**跑到一半挂了之后怎么办**。可变状态表在崩溃时只
留下「当时写到哪一步」的残影，无法回答「模型调用发出去了吗」「工具的副作用发生了吗」。
追加式日志把每个决策点都变成一条不可变事实，恢复逻辑因此可以**读事实**而不是**猜状态**。

**代价**：读放大。每次 `load()` 都要折叠。这个代价是真实的，也确实成了瓶颈——见第 10 条。

**什么时候是错的**：如果任务短到不可能被打断（比如一次纯文本补全），这套机制是纯粹的开销。
Witness 面向的是长任务、会改仓库的任务。

## 2. 前向 hash 链

**决策**：每条事件记录 `previous_hash`，`fold` 前先全链校验。

**为什么**：仅靠自增 sequence 只能发现缺号，发现不了**篡改**和**分叉**。hash 链让「有人改了
第 5 条」和「有两条不同的第 6 条」都变成可检测的错误，而不是静默的错误恢复。

**代价**：每次全量折叠都要做 O(n) 次 SHA-256；schema 演进必须冻结旧版本的 hash 编码器
（`_stored_payload_v1` 永远不能改，v2 有自己的编码器和 upcaster）。

**什么时候是错的**：如果数据库本身就在你的信任边界内、且没有审计要求，这层是多余的。

## 3. 先记意图，再执行副作用

**决策**：`tool.planned` / `tool.started` 在工具真正执行**之前**提交；`model.started` 在调用
provider **之前**提交。

**为什么**：崩溃发生在「已提交 started、结果未知」这个窗口时，恢复端至少知道**可能已经发生
过副作用**，从而可以 fail closed。反过来（先执行再记录）会产生一类无法分辨的状态：日志里
什么都没有，但钱已经花了、文件已经改了。

**代价**：每个工具调用多一次数据库往返；日志条数大约翻倍。

**验证**：`examples/chaos_resume.py` 就是专门在 `tool_started` 落库之后才 `kill -9` 的。

## 4. 工具默认「不幂等、不可并发」

**决策**：`@tool` 的默认值是 `idempotent=False, parallel_safe=False`，作者必须显式放开。

**为什么**：这两个属性一旦声明错，代价是**重复的真实副作用**（重复扣款、重复发消息）。
默认值应该指向「出错时最保守」的那一侧，让放开成为一个需要思考的动作。

**代价**：默认配置下并发度低，很多本可以并行的只读工具需要作者手动标注。

**具体体现**：`write_workspace_file` 声明 `idempotent=True`（同内容重写得到同一棵树），这是
一个**有代价的承诺**——正因为有它，崩溃后的 Resume 才敢自动重试，而不是停下来等人。

## 5. 不确定的非幂等工具 → 进人工，不自动重试

**决策**：恢复时如果发现一个非幂等工具「已 started、结果未知」，Run 进入
`NEEDS_RECONCILIATION`，等操作员选择 `retry` / `use_result` / `abort`。

**为什么**：这类状态在信息论上就是不可判定的——日志无法告诉你 provider 那边到底执行没执行。
自动重试是在赌，自动跳过也是在赌。唯一诚实的做法是停下来，把信息交给能去外部系统核实的人。

**代价**：需要人工介入，不能全自动恢复。这是**故意的**。

**替代方案**：如果工具在服务端支持幂等键（Runtime 提供了稳定的 `run_id:call_key`），就应该
声明 `idempotent=True`，把这个决定前移到设计期。

## 6. 租约不够，还要 fencing token

**决策**：租约带一个单调递增的 fence 号，每次写入都校验。

**为什么**：租约只能回答「谁**应该**在写」。它回答不了「这次写是不是当前 owner 发出的」——
进程可能因为 GC 停顿、虚拟机冻结、网络分区卡住，醒来时仍然以为自己持有租约。没有 fence，
这个「僵尸写入」会静默覆盖新 owner 的事实。

**代价**：每次写入多一次比较；租约过期后必须等 TTL 才能接管（`examples/fencing_takeover.py`
里 STEP 3 那段等待就是这个）。

**验证**：`examples/fencing_takeover.py` STEP 5 展示的正是「进程还活着、还攥着 lease 对象、
写入被拒」。

## 7. LISTEN/NOTIFY 只是提示，不承载事实

**决策**：通知只用于低延迟唤醒 follower；消费者始终按 sequence 查表，并有轮询兜底。

**为什么**：PostgreSQL 的 NOTIFY 会合并、会在连接断开时丢失。任何把「收到通知」当作「有新
事件」的设计，都会在连接抖动时丢数据。反过来，把它降级成纯粹的性能优化，正确性就完全由
「按 sequence 查询」保证。

**代价**：即使一切正常也要维持轮询路径。

**副作用**：正因为通知只是提示，`_NotificationHub` 在连不上数据库时可以直接 fail open——
waiter 退化成按自己的超时轮询，不影响正确性。

## 8. 成本未知 ≠ 0

**决策**：pricing catalog 没有匹配价格、或模型调用中断时，成本记为 `null` 并附带原因，
**绝不记 0**。汇总时只要有一条未知，总额就是未知。

**为什么**：0 是一个看起来正常的数字，会一路流进报表和告警而不触发任何怀疑。`null` 会。
这类「安静的错误」比崩溃危险得多。

**代价**：调用方必须处理 `None`，不能直接相加。

**一致性**：这条规则贯穿到评测 harness：`EvalReport.total_cost_micros` 只要有一个任务成本
未知，总额就是未知。

## 9. 可观测性不参与正确性

**决策**：telemetry 只消费**已提交**事件的安全投影；Replay 完全抑制 telemetry；exporter 失败
一律 fail open。

**为什么**：可观测性是用来在系统出问题时看清楚发生了什么的。如果它自己能让任务失败，它就
在制造它本该诊断的问题。

**代价**：Collector 挂掉时会静默丢 trace，需要独立监控 telemetry 管道本身。

**具体体现**：metric 标签走**显式 allowlist**（最多 64 项、不支持通配符）——一个高基数标签
就能拖垮整个 metric backend，所以宁可退化成 `other`。

## 10. fold 缓存不信任存储里的投影

**决策**：`load()` 在进程内缓存已折叠的 `RunSnapshot`，只读增量；但缓存**只保存本进程自己从
已校验事件链折叠出来的状态**，绝不从数据库读取快照投影。

**为什么**：这是第 2 条的直接推论。如果 `load()` 信任存储里的一行 snapshot，那么一行伪造的
snapshot 就能冒充整段历史——hash 链正是为了防这件事而存在的，不能在读路径上把它绕过去。
进程自己算出来的状态则是安全的：它来自一条已经全量校验过的链。

**代价**：新进程第一次读某个 Run 仍然要付完整校验的代价（2000 事件约 106ms）。这一列在
benchmark 里是**故意不优化**的。

**收益**：热路径从 O(n) 变成 O(1)（104ms → 0.36ms），append 从 O(n) 变成近似 O(1)
（115ms → 6.8ms）。

**守卫**：每次续折叠仍校验增量与缓存前缀之间的 hash 链接；对不上就丢缓存、退回全量折叠。
缓存只在事务**提交后**写入——提交前写会让回滚的状态被后续读到。

## 11. Session 拥有独立 Git worktree，绝不碰主工作树

**决策**：每个 Session 在受管目录下有一个 detached worktree；checkpoint 用内部 ref 固定不可变
tree；主仓库的 HEAD、index、工作区从不被修改。

**为什么**：Agent 改代码这件事本身风险就高。如果它直接在用户的工作树上操作，一次失误就可能
毁掉未提交的工作。隔离 worktree 让「回滚」变成一个廉价、可验证的操作。

**代价**：磁盘占用翻倍；跨主机迁移做不了（见非目标）。

**边界**：敏感路径（`.env`、私钥、凭据）默认拒绝——注意是**整个 worktree 校验失败**，不是
悄悄跳过那个文件。fail closed 比 fail quiet 好。

## 12. 事件按隐私分级，公共投影单独建视图

**决策**：事件分 `public` / `metadata` / `private` / `secret`；migration 创建不含
`private_payload` 的安全屏障视图 `react_agent_public_run_events`。

**为什么**：审计角色需要看执行链路，但不需要看 prompt 和工具参数。把这个区分做进 schema，
比依赖应用层每次记得过滤要可靠。

**代价**：查询要分两条路径；授权模型变复杂。

**没做的**：migration 不会擅自创建组织角色或改已有角色成员关系——那属于部署方的策略。

## 明确不做的事

写清楚非目标和写清楚目标一样重要。以下都是**知道怎么做但决定不做**的：

| 非目标 | 为什么不做 |
| --- | --- |
| **跨主机迁移 worktree** | 需要引入对象存储或共享文件系统，会把一个「单机也能跑」的系统变成必须有分布式存储。当前支持同机多进程或共享 Git 存储。 |
| **持久化 snapshot 加速冷启动** | 见第 10 条。要做对必须实现 `RunSnapshot` 的完整可往返序列化，任何一处不精确都会污染恢复决策——这是全系统最不该冒险的地方。冷启动 106ms 目前不是瓶颈。 |
| **自动重试非幂等工具** | 见第 5 条。这是设计立场，不是待办。 |
| **多租户鉴权 / RBAC** | 工作台默认只监听 `127.0.0.1`，信任边界明确交给部署方。做一半的鉴权比没有更危险。 |
| **前端做成产品** | `static/index.html` 是**调试工作台**，不是产品 UI。它假设使用者理解 durable sequence 和 reconciliation。 |
| **模型路由 / 多 provider 编排** | 与本项目要解决的问题（可恢复性）正交，会稀释主线。 |

## 已知的粗糙处

诚实记录，而不是等人发现：

- **前端 `persist()` 没有节流**：每收到一个事件就重新序列化最多 2000 条写 sessionStorage，
  长 Run 是 O(n²)。渲染有 rAF 节流，persist 没有。
- **`import react_agent` 会连带 import psycopg**：只想用 ReAct core 的使用者也得付这个代价。
- **`RuntimeStore.set_lineage` 协议签名不一致**：Protocol 声明 `str | None`，PostgreSQL 实现
  收窄成 `str`。目前唯一调用方总是传非 None，属于潜在问题而非现行 bug。
- **敏感路径行为与措辞不符**：README 说「拒绝进入 checkpoint」，实际是整个 worktree 校验
  失败。行为更严格（fail closed），但措辞应该对齐。
